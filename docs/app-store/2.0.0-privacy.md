# Manut AI 2.0.0 for the Mac App Store: App Privacy answers (item 123)

Drafted on 26 Nov 2026 from the code at `173e23af` (this branch's base), for the owner to confirm before anything is
typed into App Store Connect. Nothing here was run: every answer comes from reading code, and each one names the file
and line, or the API route, that proves it. Where the code leaves room for judgement the answer says so and the same
point is in section 3.

Things to know before reading:

- `docs/app-store.md` (item 119) is not in this branch, so the App Store edition's own changes could not be read. This
  draft assumes what the brief says: the edition leaves the updater out. It does not assume anything else about it.
  Section 3, question 12 lists what to check once item 119 merges.
- Line numbers are for this commit. They drift, so the search that found each one is in "How this was found" at the
  end.
- "Collected" below uses Apple's meaning as the owner will meet it in App Store Connect: data sent off the Mac to us or
  to a partner who handles it for us, and kept for longer than answering that one request. Data that stays on the Mac
  is not collected. Please check that reading against Apple's current App Privacy page when entering the answers.

## What the app is when it is reviewed

The app has three modes. Which of them sends anything off the Mac decides almost every answer.

| Mode | What leaves the Mac | Default |
| --- | --- | --- |
| Practice (the in-process demo) | Nothing. `apps/desktop/src/runtime/setting.ts:1-3` says a fresh install "never reaches a network", and `readRuntimeSetting` returns Practice unless the person saved Connected. | Yes, on a fresh install |
| Connected | Requests to the Manut AI API at an origin the person types in Settings › Developer, through the system `curl` (`apps/desktop/src-tauri/src/api_link.rs:5-15`, `:251`). Only `https://` (or plain http to this computer) and only paths under `/v1/`. | No, the person turns it on |
| Phone relay ("Reach this Mac from your phone") | One WebSocket to the same API origin (`apps/desktop/src/remote/link.ts`, `fromShell.ts:43`). Off until the person accepts a consent sheet (`apps/desktop/src/remote/state.ts:1-8`). The API's relay is also off for everyone outside the dev environment: `RELAY_ENABLED` is set in dev only, since 27 Nov 2026, and unset in staging and production (`apps/api/wrangler.jsonc`, `apps/api/src/relay.ts:16-18`). | No, and not yet switchable on the server |

Connected needs an account. Today the desktop can only sign in with an Apple identity token pasted by hand in
Settings › Developer (`apps/desktop/src/runtime/http/session.ts` header), and the real sign-ins (Sign in with Apple,
a code by email) wait on the owner (`docs/turning-on.md`, rows for `APPLE_CLIENT_ID` and `EMAIL_SIGN_IN`). Several
other features that store data are built and off (see the switches in `docs/turning-on.md`: LINE messages coming in,
Google Sheets, real models, artifact links, the live feed). **This draft answers for the app with those switches on**,
because the label belongs to the version, and a label that is true only while features are off becomes wrong the day
they are turned on. Each answer says which switch its data depends on. Question 1 in section 3 asks the owner to confirm
this approach.

The one thing Apple asks first: "Do you or your third-party partners collect data from this app?" The answer is **Yes**,
because of Connected mode.

## 1. What is collected

Everything collected below is **linked to the person's identity** (the API keys every record to the account's tenant, for
example `apple:<Apple's user id>`: `apps/api/src/auth.ts:199`) and **not used for tracking**. Tracking in Apple's sense
(linking with other companies' data for advertising, or giving data to data brokers) happens nowhere: there is no
advertising code, no advertising identifier, no analytics or attribution SDK, and no data sold or shared with brokers.
How that was checked is under "How this was found". Purposes are Apple's list; the only ones used are App Functionality
and, where noted, nothing else.

## 2. What is not collected, and why

**Practice mode, and everything the person does in the code editor, terminals, git and chat with their own agents.**
Nothing is sent to us. The app starts no process of its own at launch (`apps/desktop/README.md`), and the page's content
policy allows connections only to the app itself, to `wss://manut.xyz` and `wss://*.manut.xyz`, and to localhost
(`apps/desktop/src-tauri/tauri.conf.json:31`; images, fonts and media allow only the app and data or blob URLs, so no
remote image or font can be fetched). Searched the Rust and TypeScript source for every other way out: the only network
code is `curl` for the API (`api_link.rs`), `gh` and `git` run as the person's own tools, the page's two WebSockets
(`runtime/http/index.ts:179`, `remote/fromShell.ts:43`), and the updater (below). There is no HTTP client crate in
`apps/desktop/src-tauri/Cargo.toml`.

**Data that passes through the person's own accounts, which we never receive:**

- *The coding agents* (Claude Code, Codex, Cursor, OpenCode and the rest). The app starts the person's own installed
  CLI and talks to it locally. Their prompts, code and files go to that agent's provider under the person's own login,
  and the app does not copy them anywhere. The same holds for Computer use: pictures and text of windows go to the
  person's own Claude Code on the Mac, over a socket only that user can open (`apps/desktop/src-tauri/src/computer/mod.rs:1-14`).
- *GitHub and other git hosts.* Pull requests, pushes and reads go through `gh`, `glab` and `git` on the person's own
  accounts (`gh_me.rs`, `pulls.rs`, `review.rs`). A non-active account's token is held in memory for one call and wiped
  (`gh_me.rs:13`). We see none of it.
- *LINE, Google and the shop's own sites.* These are reached from the API on the shop's own credentials, and are
  covered above where the API stores anything from them.
- *Speech.* The Mac's own recogniser, with audio kept in memory (`voice.rs:10-14`). Apple's servers only for a language
  the Mac cannot do, only after the person says yes, and that is Apple's processing.
- *Usage meters of the agents.* `claude_usage.rs:1-19` keeps the numbers Claude Code reports in a file on the Mac:
  "Nothing is sent anywhere and no token is read."
- *The keychain items* (session `xyz.manut.desktop.api`/`session`, outpost, shop cache key, relay key) never leave the
  Mac as items; the session's tokens go only as a request's bearer to the API origin (`api_link.rs:1-25`, `:35`).

**The phone relay (off for everyone today).** The phone channel is end to end encrypted: the Mac and phone agree a key
the relay never holds, and the relay forwards numbered encrypted records it can neither read nor change
(`docs/remote-access.md`, "The architecture"; `docs/relay-protocol-v1.md`). What the relay sees, in the words of
`docs/remote-access.md:380-381`: "internet addresses (Cloudflare sees them; the relay object keeps only a digest),
times, byte counts, the Mac's and phones' random ids, token hashes, and from phase 4 the push address. Never content."
What its code actually stores, checked: the Mac's public key, each device's token hash (plus an optional push token),
the relay's status and last-seen time, and a day's byte count (`apps/api/src/relay-object.ts:10-13`, `:40`, `:177`,
`:339-354`; the object "logs nothing", lines 12-13). A socket carries only the digest of its source group, never the address (`relay-object.ts:28`,
`relay.ts:68-73`). The push address is not yet used ("does nothing today", `docs/remote-access.md:46-47`). Nothing from
a chat, an ask or a file is in the relay.

**The updater.** The Developer ID build checks `github.com/mygogocash/manut-ai/releases/latest/download/latest.json`
(`tauri.conf.json:90`; `apps/desktop/src/sidebar/updater.ts:39`; plugin registered at `lib.rs:1671`). That sends no
account data to us, but GitHub sees the Mac's address. The brief says the App Store edition leaves it out, so it does
not count there. Apple's rule is that the App Store build may not update itself.

## 3. Questions where the code leaves room for judgement

Each has the two possible answers and a recommendation.

1. **Answer for features that are built but switched off?** (a) Answer for the app with every switch on. (b) Answer for
   what is switched on today. *Recommend (a).* Today almost nothing stores data, but the label belongs to the version;
   under (b) it becomes wrong, and out of date with the Privacy Policy, the first time the owner turns on Sign in with
   Apple or LINE. Apple lets the owner edit the answers at any time without a new build (please confirm in App Store
   Connect), so a smaller label can be used first and widened later, but that must happen before the switch, not after.
2. **Declare the shop's customers' LINE messages as Emails or text messages?** (a) Yes. (b) No, because the writers are
   not the app's users and LINE is parked. *Recommend (a).* The API stores the message text (`pilot-store.ts:155`) and
   shows it in the Mac app; Apple's question is about what the app's backend collects, not only about the user. If
   LINE is never switched on for this release, (b) is also correct, and the label can be widened before it is.
3. **Where do the shop's website passwords go?** (a) Other user content. (b) Do not declare, because they are sealed
   and "no AI ever holds a password" (`outpost/mod.rs:1-6`). *Recommend (a).* They are sent from the Mac to our server
   and kept (sealed) until the owner removes them; being sealed does not make them uncollected. Apple has no
   "credentials" type. They are not Sensitive info in Apple's sense.
4. **Declare Device ID?** (a) Yes. (b) No, because it is a random id the app makes, not a hardware or advertising id.
   *Recommend (a).* It is sent to us, stored with the session and shown in the owner's device list, and the cost of
   saying yes is nothing.
5. **Declare Other financial info and Purchases?** (a) Yes. (b) No, because payments are recorded by an operator in the
   operator console, not from the Mac app, and payments are parked. *Recommend (a)* if the pilot's operator console
   will still hold these records when the App Store build is live, because the same shop's data is reachable from the
   app's tenant, and the memory facts may hold costs. Choose (b) only if the owner confirms no payment record exists
   for any shop that can sign in with the Mac app.
6. **Declare Other diagnostic data, given Cloudflare's logs?** (a) Yes. (b) No, because the logs are a hosting
   platform's and the API deliberately writes metadata only. *Recommend (a).* They are on at full sampling
   (`wrangler.jsonc:82-86`), they carry a task id that maps to a shop, and the app's own comment says a request's
   protocol header can land in logs (`apps/desktop/src/runtime/http/feed.ts:12-16`). The owner should open the Cloudflare
   Workers Logs settings and read what a log line actually holds; this draft could not.
7. **Is Anthropic a partner that collects?** (a) Yes, declare under Other user content (done above). (b) No, it is a
   service provider. *Recommend (a);* Apple counts data sent to third parties the app's backend uses. Check the
   Anthropic account's data terms (retention, training) before the Privacy Policy is written; this draft could not
   read them.
8. **Is anything "not linked to identity"?** (a) All linked. (b) Mark rate-limit and sign-in-code source tags as not
   linked. *Recommend (a).* The tags are not shown as a data type, and every other record is tied to the tenant.
9. **When the relay is switched on, does the label change?** (a) No: it adds only Device ID (random phone ids) and
   Other usage data (byte counts), both already declared. (b) Add a line for the addresses Cloudflare sees. *Recommend
   (a),* because the relay keeps only a digest. Re-read the label when `RELAY_ENABLED` is set and when the push address
   in phase 4 is built, since that stores a push token (`relay-object.ts:40`).
10. **The speech option that uses Apple's servers.** (a) Not collected by us, mention in the policy. (b) Declare Audio
    data. *Recommend (a);* our code never receives the audio (`voice.rs:10-14`).
11. **Computer use and the agents.** (a) Not collected (they stay on the Mac and with the person's own agent).
    (b) Declare Photos or videos for window pictures. *Recommend (a).* The pictures go only to the person's Claude Code
    (`computer/mod.rs:1-14`).
12. **Check item 119.** When `docs/app-store.md` merges, confirm that the App Store edition (a) drops
    `tauri-plugin-updater` and the `updater:default` permission, not only the check (`lib.rs:1671`,
    `capabilities/default.json`); (b) does not add a crash, analytics or review-prompt service; (c) leaves
    Connected's origin as the person's own entry. If any answer is no, section 2 and the Diagnostics rows change.
13. **In-app account deletion.** *Answered by item 124 (26 Nov 2026).* Guideline 5.1.1(v), read that day: "If your app
    supports account creation, you must also offer account deletion within the app." The app now has it: Settings ›
    General › Account › Delete account (`apps/desktop/src/settings/DeleteAccount.tsx`), which calls `POST
    /v1/account/deletion` with the person's own session (`apps/api/src/account-deletion.ts`; `docs/pilot-api.md`,
    "Deleting your own account"). For an owner it deletes the account and every shop it owns (messages, replies,
    payments, the LINE connection, team, memory, helpers' access) through the same deletion record and wipe the
    operator's flow uses; for a helper, only their account and their access. A Sign in with Apple account's token is
    revoked at Apple's `/auth/revoke`, retried if Apple does not answer. No email or support step is needed, which
    Apple's page asks of apps outside regulated industries. Two things remain for the owner: the route must be deployed
    to production before release, and the Apple settings for revoking (`APPLE_TEAM_ID`, `APPLE_KEY_ID`,
    `APPLE_PRIVATE_KEY`) set on the Worker (`docs/app-store/2.0.0.md`). What the deletion leaves, and the Privacy Policy
    should say: the record that the account was deleted (who, by a hash of the account, when, which shops), each
    deleted shop's own deletion record, and in a shop a helper left, the name the owner gave them and the shop's log of
    what they did, which are the owner's records.
14. **The outpost's page text: Browsing history or Other user content?** (a) Other user content only. (b) Also Browsing
    history. *Recommend (a).* The app does not record where the person goes; it reads named pages of the shop's own
    sites for the team and reports up to 4,096 bytes of text per step.
15. **Account sign-in by Sign in with Apple needs an email choice.** If the sign-in asks Apple for the email scope the
    address is stored (as above). If it does not, Email address from Apple drops out and the others remain. Confirm
    which scope the owner's real sign-in will request.

## 4. What the owner's Privacy Policy must say

So the policy agrees with the answers above, it needs to say, in plain words:

- **Two modes.** Practice keeps everything on the Mac and sends nothing. Connected, which the person turns on and signs
  in to, sends the items below to Manut AI's service, which runs on Cloudflare.
- **What Connected sends and keeps**, each with its reason (App Functionality) and how long: the account's Apple user
  id and, if given, verified email (sessions last up to 90 days from first sign-in); for a Sign in with Apple account, the
  refresh token Apple gives, sealed, kept only so it can be revoked when the account is deleted (item 124); the owner's and helpers' names, a
  helper's invited email or LINE id; the team's memory facts; routines; tasks and the AI team's drafts; approvals and
  the audit log (until the shop is deleted); published artifact text (until removed); the shop's site sign-ins, sealed;
  text read by the Mac's outpost; sign-in device ids; model spend. Customers' LINE messages kept 7 days; display names
  cached 7 days; operational metadata 30 days; outputs and memory until deleted (`apps/api/src/retention.ts:9-12`,
  `docs/pilot-api.md:372-375`).
- **Who else handles it.** Cloudflare (hosting, storage, logs, and sending the sign-in email); Anthropic (the AI team's
  text, once a key is set); Google (a shop's own Sheet, only the files the app made, `drive.file`); LINE (messages to
  and from the shop's own Official Account); Apple (sign-in, and speech for languages the Mac cannot do). Say that none
  of them is used for advertising and that no data is sold or given to brokers.
- **What stays off our servers.** The person's code, files, prompts and chats with their own coding agents, their
  GitHub and git traffic, voice audio, and window pictures from Computer use. Say these go to the person's own
  providers under their own accounts.
- **Phone access.** Off by default; the channel is end to end encrypted; the relay sees addresses, times, sizes and
  random ids and never content.
- **No tracking.** No advertising, analytics or crash-reporting service in the app.
- **Updates.** The App Store edition updates through the App Store only. If a Developer ID build is also offered, say
  its update check contacts GitHub, which sees the Mac's address.
- **Rights and deletion.** Say how a person exports their data (`GET /v1/tenant/export`, operator or owner session), that
  they delete their account in the app (Settings › General › Account › Delete account), which deletes the shops they
  own with it, and that an operator can also delete a shop with the owner's yes on a confirmation link; and state a
  contact address. Say what a deletion keeps (question 13) and that a Sign in with Apple account's Apple token is
  revoked.
- **Children.** The owner decides the age statement; the code has no age check.
- **Keep it true.** The policy should name the switches (LINE, Google, models, artifact links, relay) and say it will be
  updated before any of them is turned on, matching question 1.
