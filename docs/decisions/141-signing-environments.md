# Item 141: the signing secrets in GitHub Environments, and the nightly's own updater key

| Date | Decision | Why | By | Undo by |
| --- | --- | --- | --- | --- |
| 28 Nov 2026 | Building with no secret and signing in a later job that runs no repository or dependency code is designed in `docs/releasing.md` ("Signing apart from the build") and proposed as row 141b, not built | It cannot be checked without a signed run, and the signed path as it is has never run; 0.1.2's signed release gives the run to compare with. Until then the build step still holds the keys, which only the environments' branch rules (and for `release` the owner's approval) now guard | Claude | Drop row 141b |
| 28 Nov 2026 | The night's notes say that a nightly build updates only to the next nightly, and that leaving Nightly means installing the stable release | A person who reads the feed release should not have to learn it from a refused update | Claude | The line in `releaseNotes`, `.github/scripts/nightly.mjs` |
| 28 Nov 2026 | The feed job refuses a night whose signatures name another key id than `NIGHTLY_UPDATER_PUBKEY` | Tauri CLI 2.12.6 only warns when its signing key does not match the build's public key (`bundle.rs`, `sign_updaters`), so a mismatched pair would be offered to every Nightly Mac and refused by each after the download | Claude | The key check in `buildFeed` |
| 28 Nov 2026 | The nightly's build job looks for `NIGHTLY_SIGNING_PRIVATE_KEY` as its first step, before the checkout | With no key the Tauri CLI fails only when it signs, at the end of a build that spent macOS minutes | Claude | The step "Check the nightly signing key is there" |
| 28 Nov 2026 | The nightly's public key is checked before any build (`nightly.mjs updater`): one line of base64 that decodes to a minisign public key, never the stable key (read from `tauri.conf.json`). With no variable a changed night fails in the decide job and says why; an unchanged night stays green after its one cheap job | No key means builds that trust nothing. Only base64 is let through because the value is spliced into the build's `--config` JSON | Claude | The step "Check the nightly's own updater key" |
| 28 Nov 2026 | Each nightly build is made with the nightly's public key and Nightly's feed as its updater endpoint, through the `--config` merge that already sets its version | A nightly build trusts only the nightly key, so on its default Stable row (111d) it would be offered stable updates that fail its check after the download. With its own feed it updates from `nightly.json` whatever the row shows. Cost: moving between channels is an install by hand, and in a stable build the row's Nightly finds an update it cannot install, which the row should say before a stable release carries it | Claude | Drop `endpoints` from `nightlyUpdater` |
| 28 Nov 2026 | The nightly signs with a key of its own (`NIGHTLY_SIGNING_PRIVATE_KEY` and its password in the `nightly` environment, the public half in the repository variable `NIGHTLY_UPDATER_PUBKEY`) and never reads the stable updater key. Replaces the 27 Nov 2026 row of `111-licence-and-channels.md` that has the nightly "signed with the stable updater key", which was the owner's, so the owner should know | The nightly builds whatever `pilot/week-1` holds, low-risk Dependabot bumps merged on a green run included, with the key in the build's environment (the sixth read's M3). A stolen nightly key now reaches only nightly installs | Claude | Point the build step's two secrets back at `TAURI_SIGNING_*` and drop the `plugins` part of its `--config` |
| 28 Nov 2026 | The `nightly` environment lets in only `main`, not `pilot/week-1` as the security read suggested | A `schedule` runs on the default branch, and an environment's rule is matched against the run's `GITHUB_REF`, not the commit the job checks out. Cost: "Run workflow" works from `main` only, so the nightly cannot run before it is there | Claude | The environment's deployment branch rule |
| 28 Nov 2026 | The three release jobs name `release` (main and `desktop-v*` tags, the owner as required reviewer, "Prevent self-review" off, administrators' bypass off); the nightly names `nightly` on its build job only; jobs that read no signing secret name none | A secret a job reads without an environment is a repository secret, which a run of any branch can read (the sixth read's M2). Self-review would lock the owner out, since every run here starts under the owner's login. Cost: each release job waits for an approval, four per release until 141b | Claude | Remove the `environment:` lines and the two environments |
