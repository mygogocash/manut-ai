# Item 126: CI that is faster and checks many agents' branches at once

| Date | Decision | Why | By | Undo by |
| --- | --- | --- | --- | --- |
| 26 Nov 2026 | A spec file must not depend on what ran before it on the shared mock bridge: `disk-chip.spec.ts` resets it before each test and `clarify-shots.spec.ts` after its last, and `e2e-shards.mjs` states the rule | A time-balanced split gives a file new neighbours whenever the timings change; the first nine-shard run put disk-chip after clarify-shots, which leaves an interview open, and disk-chip counted its note | Claude | Remove the two resets |
| 26 Nov 2026 | Nine browser shards, not eight (replaces the row below on eight shards; the split is unchanged) | After the lead's branch was merged in, every spec file took about a quarter longer (4,216 s in all, run 45817666645): eight shards would each run about 8m 46s, and nine bring them to 7m 47s, next to `panel-max.spec.ts`'s 7m 45s alone. The runner time is the same and a full run is 18 jobs, within the organisation's 20 | Claude | Set the matrix and `--shards` back to 8 |
| 26 Nov 2026 | The Ubuntu packages Playwright installs are kept in the Actions cache (`.github/actions/playwright-browser`, apt's download folder pointed at a cached one), saved from pushes to `main` and `pilot/**` only, and a failed install runs once more | Ubuntu's mirror crawled at 130 kB/s in three of four runs on 26 Nov and held a shard up to five minutes; once it answered 404 for a package its own list named. Packages are checked by apt against the fresh lists, so a stale cache only costs a download | Claude | Call `playwright install --with-deps` directly again |
| 26 Nov 2026 | Only pushes to `main` and `pilot/**` save the Rust build cache; a helper's branch restores `main`'s | A run restores only its own branch's caches and the default branch's, so a helper branch's 1.5 GB of Rust cache served that branch alone, and the repository's caches reached 10.9 GB of the 10 GB GitHub keeps before evicting | Claude | Set `save-if` back to every push |
| 26 Nov 2026 | `faces.spec.ts` reads each face's size with `expect.poll` until it settles | With item 125d merged, the Settings page's 64px face measured 63.99999 twice in a row in one shard, still in its entrance; the size must still be exact once settled | Claude | Read the size once again |
| 26 Nov 2026 | The desktop's browser specs run as eight shards of whole spec files, balanced longest first by each file's measured time (`.github/scripts/e2e-shards.mjs`, `apps/desktop/e2e/timings.json`); a file with no time counts as the median | Playwright's `--shard` splits by test count, and six shards took from 6 to 17 minutes. `panel-max.spec.ts` alone takes 7m 54s, so eight is the fewest shards for which it is the longest; a ninth or tenth shard would shorten only the others | Claude | Set the matrix back to `--shard=i/N` in `ci.yml` |
| 26 Nov 2026 | CI writes fresh timings only as the `e2e-timings` artifact; the lead commits them with `node .github/scripts/e2e-timings.mjs <run id>` when the shards drift apart | The brief allows nothing that writes to the repository from CI, and timings from a failing run include timeouts | Claude | Commit the artifact from a scheduled job instead |
| 26 Nov 2026 | A failing desktop browser spec fails the run (no `continue-on-error`; the all-shards job is `--strict` and fails when any shard failed or left no report), and the desktop Playwright config retries a failed test once on CI | Five specs were red for hours unseen on 26 Nov. One retry lets a slow start on a shared runner show as flaky rather than red | Claude | Put `continue-on-error: true` back on the two jobs |
| 26 Nov 2026 | Web on phones is two jobs, one per engine, each running the projects whose names end in its engine (`--project="*(WebKit)"`) | One job ran both engines for 11 minutes; each now installs one browser and has its own summary and artifacts | Claude | Go back to one job installing both |
| 26 Nov 2026 | `cancel-in-progress` is false on `main` and `pilot/**` and true elsewhere; the default queue (one running, one pending, a newer run replacing the pending one) is kept, not `queue: max` | Each merge to the pilot branch cancelled the run before it, so none finished. GitHub refuses `queue: max` together with `cancel-in-progress: true`, and the run that finishes measures from the last green commit, so a replaced pending run's files are still checked | Claude | Set `cancel-in-progress: true` again |
| 26 Nov 2026 | CI runs on pushes of `feat/`, `fix/`, `refactor/`, `test/`, `docs/`, `ci/` and `chore/` branches; a branch with no green run is measured from the newest green push commit of `main` or a `pilot/` branch among the last 100 green runs that GitHub's comparison calls an ancestor, trying at most 10, and runs everything otherwise | Helpers' checks ran one at a time on the lead's Mac. The ancestor's green run saw every file up to it, so only the branch's own changes need checking | Claude | Remove the prefixes from `on.push.branches` |
| 26 Nov 2026 | The lead merges an item when CI is green on the exact commit (`finish-item.sh --ci`, `ci-wait.sh`); `gate.sh` stays for when CI is down | CI checks several items at once and runs the browser specs the gate never ran; merging by SHA after re-checking that nothing moved keeps what merges equal to what was checked | Claude | Finish without `--ci` after `gate.sh` |
